## Read-only installer scope-review progress (2026-11-08)

- `go/internal/windows/volumereview/` now produces a deterministic **non-authorizing** scope review and snapshot fingerprint. Its typed changes distinguish volume additions/removals, full-width volume identity replacement, root-policy additions/removals, and any policy alteration. The review is order-independent and excludes drive-letter aliases from identity binding.
- `BuildFreshInstall` / `RevalidateFreshInstall` explicitly reject an existing-FI baseline in the intended v2 installer workflow. No v1.1-to-v2 upgrade or in-place policy update is supported.
- `volumereview.Revalidate` refuses stale/mismatched native observations, changed proposed/old configurations, and modified review fields. SHA-256 provides a deterministic reference only; it is **not a signature or a protected approval receipt**.
- Branch-only `fi-install.exe -list-volumes -volume-config <path>` now includes `requested_scope_review` in its non-mutating JSON report. Existing `1.1` installation/service startup is untouched. See `docs/development/WINDOWS-VOLUME-FIRST-SCOPE-REVIEW.md`.
- Still not implemented: authenticating an administrator's approval, protected host-bound v2 config/receipt installation, installer-bound root-object identity approval and audit/SACL authorization, transactional rollback, broker selection at service startup, volume worker custody, and backend changes.


## Signed installer transaction-intent verification (2026-11-08)

- `go/internal/windows/volumeconsent/receipt.go` now verifies short-lived, host-bound signed **installer intent** using CNG-compatible ECDSA P-256/SHA-256. It checks a separately trusted public key, native machine SID, protected installation ID/approval generation, old/new scope digest and an exact fresh `volumereview` comparison.
- Tests cover valid signatures, incorrect trusted key/curve, malformed/duplicate JSON, changed host/installation/sequence, stale installed configuration, expiration, tampered policy and changed native volume. The branch also implements strict P-256 Windows CNG raw-signature-to-DER conversion, with end-to-end receipt verification and malformed scalar tests. Test-only signing keys are ephemeral in-memory values; none are stored in this repository.
- **Not implemented:** production CNG signer/issuer trust, native operator authentication, protected instance/generation state, transactional v2 config/receipt installation, durable installed grant and service handoff. Exported volume broker startup remains blocked by `ErrVolumeModeRequiresApproval`.
- See `docs/development/WINDOWS-VOLUME-FIRST-CONSENT-RECEIPT.md`.

## Durable installed-grant verification (2026-11-08)

- `go/internal/windows/volumegrant/` independently verifies a domain-separated ECDSA P-256 signed durable v2 scope grant against a separately pinned exact-envelope digest, committed generation and predecessor, native host/installation identity inputs, canonical scope digest and a distinct full-operational-configuration digest. It additionally hashes the **actual provided operational bytes**, rejecting empty, oversized or changed runtime configuration content; future complete v2 semantic validation is still required. Tests prove that a correctly signed but uncommitted grant is rejected and old signed grants cannot substitute for a later protected generation.
- `volumeconsent.VerifyFreshInstall` requires first-install sequence 1 with no previous config, and `volumegrant.VerifyFreshInstallation` requires grant generation 1 with no predecessor. These are the future v2 installer entry points, not update APIs.
- The new verifier is **only a pure verification component**. No trusted Windows state storage, key provisioning, native signing/administrator consent, transactional installer mutation, service-startup verifier or durable authority handoff is implemented. Installed FIUSNReader remains root-centric and the exported volume-mode broker startup refuses activation.
- See `docs/development/WINDOWS-VOLUME-FIRST-INSTALLED-GRANT.md` and `docs/development/WINDOWS-VOLUME-FIRST-CONSENT-RECEIPT.md`.

## Creation-only transaction evidence (2026-11-08)

- `go/internal/windows/freshinstall/creation_journal.go` now defines an eight-step, strictly ordered, **creation-only** v2 installer journal protocol with a durable write-ahead intent before each prospective native mutation, a creation-verified acknowledgement and explicit terminal completion. The package-private resource-creation runner has only test/mock interfaces; a separate private Windows-native **journal write/sync** backend exists but is not connected to installer activation or native FI resource creation.
- Journal events also bind the exact prepared scope, operational-configuration, signed approval-receipt and initial signed-grant SHA-256 values. Bounded canonical JSON event replay rejects missing, duplicated, rearranged, truncated, oversized or cross-install records, and refuses midstream artifact-digest substitutions. SHA-256 event chaining is order/corruption evidence, **not trusted provenance**. An intent without a verified acknowledgement or missing terminal completion forces an **in-doubt manual-recovery** result; no automatic deletion or retry is authorized.
- The runner now also requires an exclusive `ReserveNew` call before any journal entry or native creation. Its mock tests refuse duplicate attempts against both completed and in-doubt transactions. Future Windows-native code must implement atomic create-new ownership under a verified protected parent. Failure-injection tests cover the reservation, durable Begin/intent/acknowledgement failures, native ambiguous partial creation and incomplete crash tails. See `docs/development/WINDOWS-VOLUME-FIRST-CREATION-JOURNAL.md`.
- A private Windows-native journal I/O writer now exists in `freshinstall/creation_journal_windows.go`: it opens and retains a no-delete-share native directory handle, checks reparse ancestors and file/directory handle types, creates a fixed journal filename with Windows `CREATE_NEW` and no file sharing, and flushes each bounded record. Windows runner tests use temporary directories; **no production native protected-parent authority or installer entry point exists**. Full `adminbox` privileged acceptance has not occurred.
- `freshinstall/bootstrap_windows.go` now supports a **private**, fixed-name `FI-Installer` child reservation with protected SYSTEM/Administrators DACL supplied through `NtCreateFile(FILE_CREATE)` rooted on the retained parent handle, native returned-child and retained parent handle checks, no-delete-share, exact policy verification, and collision/in-doubt refusal. It does **not** attest trusted `ProgramData` ancestry, require an approved operator token or connect to installer apply. See `WINDOWS-VOLUME-FIRST-PROTECTED-BOOTSTRAP.md`.
- The native creation-journal writer now requires an actual retained directory-handle owner/protected DACL check before `CREATE_NEW` and a newly created journal-file handle owner/inherited DACL check before acknowledging its reservation. `journal_parent_policy.go`, `journal_parent_security_windows.go`, `journal_file_policy.go`, and `journal_file_security_windows.go` provide the strict policy and Windows native security descriptor extraction. Earlier temporary-directory file I/O fixtures explicitly opt into a `_test.go`-only bypass. The separate bootstrap collision root remains in the preflight inventory. **Authenticated protected-parent provenance/issuer trust, creation-journal orchestration and native v2 installer apply are still missing.** See `docs/development/WINDOWS-VOLUME-FIRST-JOURNAL-PARENT-SECURITY.md`.
- Remaining: protected journal-parent provisioning and proven ACL/ancestor identity at creation time, Windows-native trusted installation lock, independently authenticated signer/receipt, exclusive creation of FI program/data/config/SCM artifacts, ownership-scoped rollback, state commit and runtime service handoff. Nothing is wired into installed services.
